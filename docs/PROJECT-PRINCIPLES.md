# Halpha Monitor 项目原则

## 文档职责

本文是 Halpha Monitor 稳定价值取向、仓库边界、复用顺序和复杂度约束的唯一语义所有者。`README.md` 说明当前已经实现的能力和实际运行方法，`AGENTS.md` 只提供 AI 工作入口，开发 Skill 只规定具体工作方法。不要在这些文件之间复制整套规则。

Halpha Monitor 是单人、自有资金、个人长期维护项目的一部分。设计应服务当前真实需求，不套用机构级治理、高可用、合规平台或团队协作假设。

## 最终价值与取舍顺序

项目的最终价值是：通过更及时、准确地识别机会、风险和未知，帮助用户改善长期、可归因、扣除真实成本后的风险调整净盈利。监控本身不产生收益，也不承诺盈利；若一项能力不能改善当前交易决策、风险判断或故障发现，就不应仅因“以后可能有用”而建设。

发生取舍时，依次优先：

1. 数据真实、时间边界明确、失败可见，不把陈旧、缺失或推测值伪装成当前事实；
2. 对当前用户决策有直接价值；
3. 个人可以理解、验证、运行、排障和删除；
4. 最后才是通用性、形式完整度和未来扩展性。

## 独立边界

- 本仓库是独立的公开市场监控服务，不是 Halpha 产品运行时，也不是交易控制面。
- 只使用公开市场接口或用户明确提供的非敏感监控输入；不得读取交易 API Key、账户数据、产品数据库、产品配置或内部控制状态。
- 不调用会改变交易所、账户或 Halpha 产品事实的接口，不发送订单，不启动或停止产品交易进程。
- 只修改本服务自己的配置、缓存、日志和 SQLite 数据库。与其他仓库通过明确的公开输出或人工决策衔接，不通过代码导入或隐式共享状态耦合。

本机绝对路径、非回环 IP、配置或业务内容中的个人邮箱、用户名、主机名、SID、MAC 地址、代理、环境变量实值、完整异常栈和已启用的本地配置属于本地隐私，不进入 Git 文件、页面输出或可外发诊断；通过命令行、用户级环境变量或仓库外文件注入。Git author/committer 邮箱是所有者选择的提交身份，可以进入提交元数据，不由本地隐私门禁改写或阻断。仓库示例只使用回环地址、公开服务端点、示例域名和合成值。回环地址与上游官方公开 API 本身不是本地隐私，不应为隐藏它们破坏可运行说明。提交与推送前必须通过仓库内隐私门禁；门禁只报告类别与位置，不回显命中内容，也不得通过跳过 hook 发布。

外网通信只用于当前监控明确需要的公开市场读取，并只向官方或已核验公开来源发送协议所需的最小请求字段。不得装载本机凭据、Cookie、账户事实或产品配置，不接入遥测、行为分析、崩溃收集、外部 Webhook、日志、原始响应、SQLite 或制品自动上传。用户提供本地输入不等于授权上传；新增外部目标或任何上传必须取得对该具体外部效果的明确授权。网络连接必然向直接目标或代理暴露出口 IP，系统不得宣称消除该传输层事实，也不得在载荷、查询或诊断字段中主动附加本机、内网或出口 IP。

## 新能力价值门槛

新增监控、指标、页面或基础设施前，必须能够简短回答：

- 当前哪项决策、风险或故障由谁消费；
- 用户最终会看到或使用什么结果；
- 数据来源、时间含义、有效截止点和未知状态是什么；
- 现有页面、外部工具或成熟库为什么不能满足；
- 最小可验证结果是什么，何时应停止或删除。

没有当前消费者、没有可见结果，或维护成本高于预期决策价值时，默认不做。优先删除、复用现有能力、人工处理或使用外部工具。

## 复用与自研顺序

按以下顺序选择实现：

1. 复用仓库现有且已锁定验证的组件和统一事实；
2. 使用维护中的成熟库、官方 SDK 或官方公开 API；
3. 在受支持接口上组合，或增加薄适配层处理本项目特有字段语义；
4. 仅在存在具体语义缺口和明确消费者时，编写边界清晰、可独立测试的最小自研代码。

不要为了减少几行适配代码而引入大型框架，也不要重复实现 HTTP、重试、解析、统计、持久化或生命周期管理中已有成熟方案。新依赖必须降低全生命周期复杂度，而不只是缩短首次编码时间。

## 默认架构与复杂度边界

在实际需求证明需要改变之前，保持：一个进程、一个 FastAPI 服务面、一个 SQLite 数据库、显式内置监控注册、有限线程、有限缓存、有限保留期和本机回环绑定。

默认不引入微服务、消息队列、插件平台、工作流引擎、第二数据库、通用告警平台、企业权限系统或高可用编排。只有已经观察到的重复瓶颈无法由现有结构解决，并且替代方案降低整体理解、运行和故障恢复成本时，才允许增加这类机制。

同一事实只保留一个权威实现；页面、API 和存储应投影它，而不是各自重新计算。

## 数据、限频与长期运行

- 每个外部事实都应保留来源身份、观测时间、数据自身时间、有效截止点、单位和必要的质量状态。
- 空值、陈旧值、部分失败和不可用必须显式表达；不得用旧缓存、零值或估算值冒充新事实。
- 遵守上游超时、频率和 `Retry-After` 等语义。临时网络错误与限频采用有上限的退避和抖动，并隔离到单个监控；永久错误或数据契约变化应清晰暴露。
- 重启后从当前事实继续，不无界重放已失去价值的积压采集；配置、事务、线程、队列、缓存、日志和历史保留均应有界。
- 关闭流程应停止采集、完成或回滚当前写入并释放资源。长期运行设计必须覆盖网络中断、恢复、部分源异常和进程重启。

## 用户界面事实契约

- 正确、无误、可直接使用是页面所呈现标准数据的默认契约，不以“已核验”“准确”“正常”等重复徽标、列或筛选项强调。无标记即表示该数据满足当前页面的数据契约。
- 主决策视图只呈现满足契约的事实。候选、缺失、陈旧、冲突、不确定或质量门未通过的记录不得混入后再要求用户逐条确认；应隔离在主视图之外，或在确有决策价值时以具体异常原因显式标注。
- 徽标和强调色只表达会改变用户判断的业务差异、时效优先级或异常，不表达所有数据共同具备的基础可信度。来源运行状态、采集积压和技术诊断默认置于次级入口，不得挤占面向交易决策的首屏。
- 人工入口用于纠错和补充，不是获得正常可用结果的必经流程。页面不得把采集器、系统或维护者应完成的质量判断转嫁给最终用户。
- 用户可见文案必须使用日常、具体、无歧义的语言，直接说明发生了什么以及会影响哪些展示或判断。不得把内部状态、比喻或流程术语直接呈现给用户，也不得用含义不明的括号说明补救含糊标题；不可避免的技术词必须就地解释。异常文案至少包含具体问题和用户可见影响，并以界面或投影回归测试防止退化。
- 首屏不得用常驻横幅或方法提示重复数据来源、基础质量契约、无标记含义、通用免责声明、控件显然行为等默认设计要求，也不得用其他低价值说明挤占决策信息。只有会改变当前判断、操作或异常处置的信息才常驻展示；必要的分类或字段规则应靠近对应控件，以悬浮和键盘可访问的方式按需解释，无内容时不保留占位。
- 会改变主表解读、完整性或可用范围的警告必须出现在主表之前或紧邻对应字段，不得放在页面末尾等待用户偶然发现；无实际影响时不显示。技术诊断统一收在监控控制旁的次级入口中按需展开，不在主内容底部堆放维护信息。
- 当监控列表已经逐项表达运行状态时，不再增加重复的汇总统计面板。必要控件与警告之后的剩余首屏空间优先留给主决策表格；不得为了放置重复统计、诊断或来源状态而人为压缩一屏可比较的记录数量。
- 主导航可以为主决策区让出空间，但折叠后必须保留可辨识的监控名称、当前项和运行状态，并继续支持直接切换；长页面滚动时不能让导航入口随页面消失。窄屏可使用更适合当前宽度的完整导航，不强制沿用桌面折叠形态。
- 以长列表为主要决策面的情报监控使用页面自身的纵向滚动，不再嵌套独立纵向滚动区；超宽字段仍只在表格区域横向滚动，并在表格尚未滚到底部时保持横向滚动入口可见。记录较多时必须分页，并先对全部筛选结果完成排序再截取当前页，不能把“当前页排序”冒充全量排序。长页面提供不遮挡主内容的回到顶部入口。
- 累计值、执行天数、均价等衍生事实必须在计算前冻结事件粒度和覆盖区间。历史只覆盖局部时，应展示明确的时间窗口或最低值，不得把局部合计写成完整事件累计；来源未披露所需粒度时保持为空，不以起止日期、公告数量或其他代理量推算。
- 面向决策的综合指标必须能说明有效输入、权重口径和覆盖度。缺失输入不得填零或默认为有利，应降权回到中性或停止出分；未经前瞻或样本外收益校准的规则分只能用于研究排序，不得命名或呈现为上涨概率、推荐买入、预期收益或仓位。
- 决策表格按可比较、可独立排序的事实拆列，不把股数、金额、价格或比例等不同量纲塞进一个排序字段；能由整行点击完成的详情动作不再占一列。购买资格等短状态应靠近证券主体以紧凑标识表达，日期只保留当前决策所需精度；证券名称可在不改变本机状态的前提下跳转到明确标注的公开行情页。

## 开发与验证

以最小的端到端结果迭代：先明确当前决策价值，再实现数据获取、存储、API 和用户可见投影中真正需要的部分。验证范围随影响扩大，至少覆盖适用的正常、空、畸形、陈旧、部分失败、限频、断网与恢复路径，以及持久化原子性、重启、保留期、API/UI 和清洁退出。

新增或修改本机 Web 页面、API 或页面投影时，“完成”必须包含把新版本运行在用户约定的常规服务入口，并提供已经实际核验的可访问 URL。临时端口、测试客户端、截图或仅通过自动化测试只能作为验收手段，不能替代运行态交付；若缺少重启权限、运行环境或其他必要条件，应明确报告阻塞与所需动作，不得把仍由旧进程提供的页面称为已交付。

开发和验收产生的任务专属临时服务、监听端口、进程、线程、浏览器会话、数据库、日志、下载、截图、缓存和目录必须有明确所有者与有限生命周期，并在交付前停止、释放或清理，再以进程、端口和路径复查确认。只保留用户需要持续访问的常规服务和明确命名的持久制品；不得遗留重复采集进程、持续占用端口的验收服务或连接真实运行库的临时实例，也不得为了清理当前任务而删除无法确认归属的共享缓存或其他工作成果。

现阶段不配置或新增 GitHub CI / GitHub Actions；测试、静态检查、隐私门禁、启动与页面回归均按变更影响在本地执行并如实报告，不为形式完整度承担远端队列、配置和维护成本。只有当工程复杂度已经实质增加，本地流程反复遗漏同类问题、合并回归频繁出现，并且自动化远端门禁成为迫切且可验证的解决手段时，才重新评估 GitHub CI。重新引入前必须记录实际失败模式、预期拦截价值和最小检查集合；若达到该门槛，CI 仍应保持短时、确定性且无需外网，真实公网读取、宽范围回归、长时间稳定性和高成本验证继续留在本地。
